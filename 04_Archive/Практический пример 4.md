# Практический пример 4: Архитектура платформы автоматизированной доставки «Baltic Express»

> **Контекст:** Логистический оператор «Baltic Express» осуществляет доставку «последней мили» для интернет-магазинов в Таллинне и Риге. Компания масштабирует ИТ-инфраструктуру и переходит на полностью автоматизированную обработку заказов, расчет маршрутов курьеров и интеграцию с внешними маркетплейсами. 
> 
> **Задача:** Разработать полный комплект системной архитектуры для нового модуля автоматического распределения заказов: от высокоуровневых потоков данных до сущностей базы данных и алгоритмов принятия решений.

---

## 📋 Исходные требования к системе (Business Requirements)

1. **Прием заказа:** Заказ поступает от интернет-магазина через REST API или Webhook. Система валидирует адрес, вес и габариты посылки.
2. **Маршрутизация (DMN):** На основе веса, срочности и зоны доставки система автоматически определяет тариф и назначает оптимальный районный склад.
3. **Распределение курьеров:** Система запрашивает GPS-координаты активных курьеров, рассчитывает оптимальный порядок доставки и формирует путевой лист.
4. **Уведомления:** Получатель получает SMS/Telegram со ссылкой на трекинг-карту и таймслотом прибытия курьера.

---

## 🎯 Практическое задание (Architecture Sprint)

Спроектируй четыре ключевые артефакта архитектуры для решения задачи:
1. **DFD (Data Flow Diagram, Уровень 1):** Показать потоки данных между внешними участниками, хранилищами и процессами обработки заказа.
2. **BPMN 2.0:** Описать сквозной процесс обработки и доставки с развилками (выбор тарифа и обработка ошибок доставки).
3. **ERD (Entity-Relationship Diagram):** Спроектировать реляционную структуру базы данных (сущности: `Client`, `Order`, `Courier`, `Warehouse`, `DeliveryRoute`).
4. **UML Sequence Diagram:** Опосредовать взаимодействие сервисов при поступлении заказа через Webhook и назначении курьера.

---

## 🛠️ Решение и Архитектурные Артефакты

### 1. DFD (Data Flow Diagram — Потоки данных)
Диаграмма потоков данных показывает, как информация циркулирует в системе между внешними источниками и внутренними хранилищами.

```
[ Интернет-магазин ] ──( 1. API Заказ )──► ( 1.0 Обработка заказов )
                                              │
                      ┌───────────────────────┴───────────────────────┐
             ( 2. Данные заказа )                            ( 3. Статус курьера )
                      ▼                                               ▼
         { Хранилище БД: Orders }                         { Хранилище БД: Couriers }
                      │                                               │
                      └───────────────────► ◄─────────────────────────┘
                                           │
                                  ( 4. Маршрутный лист )
                                           ▼
                                 [ Курьер «Baltic Express» ]
```

### 3. ERD (Entity-Relationship Diagram — Схема базы данных)
Реляционная структура данных в PostgreSQL / Supabase:

- **Client** (`id`, `name`, `phone`, `email`, `created_at`)
- **Warehouse** (`id`, `city`, `address`, `capacity`)
- **Courier** (`id`, `name`, `vehicle_type`, `current_lat`, `current_lon`, `status`)
- **Order** (`id`, `client_id` (FK), `warehouse_id` (FK), `weight`, `delivery_address`, `status`, `created_at`)
- **DeliveryRoute** (`id`, `order_id` (FK), `courier_id` (FK), `assigned_at`, `delivered_at`)

*Связи:*
- `Client` 1 ── M `Order`
- `Warehouse` 1 ── M `Order`
- `Order` 1 ── 1 `DeliveryRoute`
- `Courier` 1 ── M `DeliveryRoute`
