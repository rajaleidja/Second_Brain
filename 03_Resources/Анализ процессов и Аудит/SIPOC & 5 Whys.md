### 1. Что это такое?

Если **BPMN** и **Process Flow** описывают то, _как процесс должен работать_, а **Scrum/Kanban** задают ритм движения задач, то **SIPOC** и **5 Why (5 Почему)** — это главные инструменты **бизнес-анализа, аудита и поиска проблем (Root Cause Analysis)** из методологии Lean / Six Sigma.

- **SIPOC** дает _верхнеуровневый взгляд_ на процесс от входа до выхода, чтобы очертить его границы и понять context.
    
- **5 Why** позволяет _пробить симптомы насквозь_ и докопаться до фундаментальной первопричины сбоя или неэффективности.
    

### 2. SIPOC: Верхнеуровневый аудит границ процесса

**SIPOC** — это табличный фреймворк, который раскладывает любой процесс на 5 базовых составляющих:

Plaintext

```
┌───────────────┬───────────────┬───────────────┬───────────────┬───────────────┐
│ S - Suppliers │ I - Inputs    │ P - Process   │ O - Outputs   │ C - Customers │
│ (Поставщики)  │(Входы/Ресурсы)│ (Процесс)     │ (Выходы/Итог) │ (Потребители) │
├───────────────┼───────────────┼───────────────┼───────────────┼───────────────┤
│Кто поставляет │ Что нужно для │ 4-7 ключевых  │ Что получается│ Кто получает  │
│данные/ресурсы?│ начала работы?│ шагов процесса│ на выходе?    │ результат?    │
└───────────────┴───────────────┴───────────────┴───────────────┴───────────────┘
```

#### Правило заполнения (Техника «Сзади наперёд»):

Аудит по SIPOC эффективнее проводить в следующем порядке: **P ➔ O ➔ C ➔ I ➔ S** (сначала определяем шаги процесса, затем готовый результат и его клиента, и лишь потом — что требуется на входе и от кого).

#### Пример SIPOC для процесса «Автоматическая обработка отзывов отеля ИИ-агентом (n8n + Gemini + Postgres)»:

|**S (Suppliers)**|**I (Inputs)**|**P (Process)**|**O (Outputs)**|**C (Customers)**|
|---|---|---|---|---|
|**Система бронирования / Webhook**|Необработанный CSV / JSON с отзывом|**1.** Прием события через Webhook|Сформированная запись в PostgreSQL|Команда управляющих отеля|
|**API Gemini**|Промпт + сырой текст|**2.** Парсинг и скоринг тональности|Алерт в Telegram о негативном отзыве|Менеджеры службы поддержки (QA)|
|**База данных Postgres**|Конфиги и справочники|**3.** Сохранение метрик в DB|Сводный отчет за сутки|Analytics / Dashboard|
|||**4.** Отправка notification в ТГ|||

> 💡 **Зачем нужен SIPOC при аудите:** Он защищает от «зарывания в детали». Если у вас ломается процесс, SIPOC сразу показывает: проблема в некачественных входящих данных (**Inputs**), плохих поставщиках (**Suppliers**) или на конкретном шаге (**Process**).

### 3. Метод 5 Why (5 Почему): Поиск корневой причины (Root Cause Analysis)

Метод, разработанный Сакити Тоёдой (основателем Toyota), помогает отделить **симптомы** проблемы от её **истинной причины**.

Суть метода: при возникновении инцидента или сбоя вы задаете вопрос «Почему это произошло?» последовательно **5 раз** (или пока не упретесь в системную ошибку).

#### Пример аудита сбоя на проекте:

> **Проблема:** Упал продакшен-сервер, сервис n8n не смог обработать отзывы.

1. **Почему упал сервис?**
    
    — _Потому что БД PostgreSQL исчерпала лимит подключений и перестала отвечать._ (Симптом 1)
    
2. **Почему БД исчерпала лимит подключений?**
    
    — _Потому что n8n workflow при обработке списка отзывов открывал новое соединение на каждый элемент и не закрывал его._ (Симптом 2)
    
3. **Почему скрипт открывал соединения таким образом?**
    
    — _Потому что разработчик не применил Connection Pooling при написании логики._ (Ошибка реализации)
    
4. **Почему разработчик не применил Connection Pooling?**
    
    — _Потому что в проекте отсутствовали регламенты и архитектурный чек-лист по работе с базами данных._ (Процессная ошибка)
    
5. **Почему отсутствовал архитектурный чек-лист?**
    
    — **Корневая причина (Root Cause):** _В команде не проводился этап проектирования (ERD / Architecture Review) перед отправкой задач в разработку._
    

#### Правила применения 5 Why:

- **Не ищите виноватых людей, ищите бреши в системах и процессах.** Ответ не должен быть «Вася ошибочно написал код». Ответ должен быть: «В системе CI/CD отсутствовал автоматический тест/линтер».
    
- **Логика должна работать в обе стороны:** Проверьте цепочку с конца в начало с помощью союза «следовательно» (Так как не было Architecture Review ➔ не было чек-листа по DB ➔ разработчик не сделал Connection Pool ➔ исчерпались соединения ➔ упал сервис).
    

### 4. Как применять SIPOC и 5 Why в связке

Plaintext

```
  ┌────────────────────────────────────────┐
  │ 1. SIPOC                               │
  │ Очерчиваем процесс и находим проблемную│
  │ зону (вход, шаг процесса, выход)       │
  └───────────────────┬────────────────────┘
                      │
                      ▼
  ┌────────────────────────────────────────┐
  │ 2. 5 WHY                               │
  │ Проводим допрос с пристрастием и       │
  │ докапываемся до корневой причины       │
  └───────────────────┬────────────────────┘
                      │
                      ▼
  ┌────────────────────────────────────────┐
  │ 3. ACTION PLAN (SMART / JIRA)          │
  │ Заводим задачу в Jira на исправление   │
  │ именно системной причины               │
  └────────────────────────────────────────┘
```

### 5. Полный систематизированный стек инструментов

Теперь в твоей базе знаний есть весь набор инструментов — от аудита проблем до проектирования и реализации:

Plaintext

```
[ БИЗНЕС-АНАЛИЗ И АУДИТ ПРОЦЕССОВ ]
  ├── Lean Canvas / VPC / JTBD   ──► Оценка продукта, ценности и пользователей
  ├── SIPOC                      ──► Верхнеуровневый аудит процессов (Suppliers-Inputs-Process-Outputs-Customers)
  └── 5 Why                      ──► Поиск корневых причин сбоев (Root Cause Analysis)

[ СТРАТЕГИЯ, ЦЕЛИ И КОМАНДА ]
  ├── OKRs & SMART               ──► Постановка целей (OKR) и четких задач (SMART)
  ├── RACI / RASCI Matrix        ──► Распределение ролей и ответственности (A, R, C, I)
  ├── Матрица Эйзенхауэра        ──► Важно / Срочно (Личный фокус на Q2)
  └── MoSCoW / RICE / Kano       ──► Приоритезация бэклога задач и фич

[ ИСПОЛНЕНИЕ И МЕТОДОЛОГИЯ ]
  ├── Scrum                      ──► Итерации (спринты), роли, события
  └── Kanban / Scrumban          ──► Непрерывный поток, WIP-лимиты

[ АРХИТЕКТУРА И МОДЕЛИРОВАНИЕ ]
  ├── TOGAF & ArchiMate          ──► Бизнес 🟡 + Софт 🔵 + Инфраструктура 🟢
  ├── BPMN / CMMN / DMN          ──► Процессы, кейсы, правила решений
  ├── Process Flow (Flowchart)   ──► Пошаговые алгоритмы
  └── UML                        ──► Диаграммы Sequence, Class, Use Case

[ ДАННЫЕ И ИНТЕГРАЦИИ ]
  ├── DFD                        ──► Потоки данных
  ├── ERD                        ──► Схемы баз данных (PostgreSQL / Supabase)
  ├── ETL Framework              ──► Конвейеры обработки данных
  └── CRUD                       ──► Операции базы данных и REST API

[ ОРГАНИЗАЦИЯ И ТРЕКИНГ ]
  ├── Jira                       ──► Иерархия (Epics / Tasks / Sub-tasks)
  └── Obsidian                   ──► MOC / ACCESS / PARA
```

### 💡 Как использовать в вашей базе знаний:

В папке `03_Resources / Анализ процессов` создай документ `SIPOC_and_5_Why.md`.

Используй **SIPOC** при первом знакомстве с новым процессом или проектом, а **5 Why** включай на этапах Ретроспективы (в Scrum) или после любых инцидентов (Post-mortem анализ).
