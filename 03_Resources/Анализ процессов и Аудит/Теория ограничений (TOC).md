[[_MOC frameworks]]

### 1. Что это такое?

**Теория ограничений (Theory of Constraints / TOC)** — это методология управления системными процессами, разработанная доктором Элияху Голдраттом (впервые описана в его знаменитом бизнес-романе _«Цель»_).

Главный постулат TOC звучит так:

> **Пропускная способность любой системы определяется ее самым слабым звеном (бутылочным горлышком / Bottleneck).**

Попытка оптимизировать любой шаг процесса, **кроме узкого места**, является иллюзией и приводит лишь к накоплению незавершенного производства (WIP) или лишним затратам, но не увеличивает общий результат системы.

Plaintext

```
  ┌───────────┐      ┌───────────┐      ┌───────────────┐      ┌───────────┐
  │  Этап 1   ├─────►│  Этап 2   ├─────►│    Этап 3     ├─────►│  Этап 4   │
  │ (100 ед/ч)│      │ (80 ед/ч) │      │  (УЗКОЕ МЕСТО)│      │ (120 ед/ч)│
  └───────────┘      └───────────┘      │   (30 ед/ч)   │      └───────────┘
                                        └───────┬───────┘
                                                │
                                                ▼
                                   Максимальная скорость системы
                                       равна СТРОГО 30 ед/ч!
```

### 2. 5 фокусирующих шагов TOC (5 Focusing Steps)

Голдратт предложил цикличный алгоритм из 5 шагов для непрерывного улучшения любой системы:

Plaintext

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. IDENTIFY (Найти)                                             │
│ Определить узкое место системы (где скапливается очередь?).     │
├─────────────────────────────────────────────────────────────────┤
│ 2. EXPLOIT (Использовать по максимуму)                          │
│ Выжать 100% из текущего ограничения БЕЗ дополнительных инвестиций.│
├─────────────────────────────────────────────────────────────────┤
│ 3. SUBORDINATE (Подчинить)                                      │
│ Подчинить всю остальную систему ритму работы узкого места.      │
├─────────────────────────────────────────────────────────────────┤
│ 4. ELEVATE (Расшить / Увеличить)                                │
│ Инвестировать ресурсы в расширение ограничения, если шага 2 мало.│
├─────────────────────────────────────────────────────────────────┤
│ 5. REPEAT (Повторить)                                           │
│ Предупредить инерцию! Найти новое узкое место и начать заново. │
└─────────────────────────────────────────────────────────────────┘
```

#### Разбор 5 шагов на примере IT-разработки / сервиса:

1. **Найти ограничение:** В команде 5 разработчиков пишут код быстро, но 1 QA-инженер не успевает тестировать. На этапе «Тестирование» в Jira скапливается 40 задач. _Узкое место = QA_.
    
2. **Использовать по максимуму:** Запретить QA выполнять задачи, не относящиеся к тестированию (например, ходить на лишние митинги). Разработчики должны подавать QA только идеально подготовленные задачи с автотестами.
    
3. **Подчинить систему:** Разработчики снижают темп написания нового кода и помогают писать автотесты или подготавливать тестовые данные для QA, чтобы ограничить WIP в колонке «Testing».
    
4. **Расшить ограничение:** Нанять второго QA, внедрить автоматический CI/CD-пайплайн с автотестами.
    
5. **Повторить:** Теперь QA тестируют мгновенно, но узкое место сместилось на этап _Деплоя на прод / Настройки инфраструктуры DevOps_. Возвращаемся к шагу 1.
    

### 3. Концепция Барабан-Буфер-Канат (Drum-Buffer-Rope / DBR)

Для операционного управления потоком в TOC используется модель **DBR**:

- **Барабан (Drum):** Ритм работы узкого места. Именно оно задает темп работы всей компании/команды.
    
- **Буфер (Buffer):** Запас времени или задач перед узким местом. Он гарантирует, что узкое место **никогда не будет простаивать** из-за сбоев на предыдущих этапах.
    
- **Канат (Rope):** Механизм ограничения передачи новых задач в систему. Новая задача берется в работу (вход в поток) **только тогда**, когда узкое место «проглотило» предыдущую задачу.
    

### 4. Связка TOC с другими методологиями

|**Методология**|**В чем фокус?**|**Связь с TOC**|
|---|---|---|
|**Kanban**|Визуализация и ограничение WIP|WIP-лимиты в Kanban — это реализация «Каната» (Rope) из TOC.|
|**SIPOC / BPMN**|Структура и моделирование процессов|Помогают на шаге 1 (_Identify_) найти, на каком именно шаге процесса возникает пробка.|
|**5 Why / Исикава**|Поиск корневых причин|Помогают на шаге 2 (_Exploit_) понять, почему узкое место теряет производительность.|
|**RICE / MoSCoW**|Приоритезация задач|Задачи, направленные на расширение узкого места, всегда получают максимальный Impact в RICE.|

### 5. Полная систематизированная матрица фреймворков

Твой арсенал менеджмента, системного анализа и разработки теперь включает полный спектр мировых стандартов:

Plaintext

```
[ ОПТИМИЗАЦИЯ СИСТЕМ И ПОТОКОВ (TOC & LEAN) ]
  ├── Теория ограничений (TOC)   ──► Поиск и расширение узких мест (5 Focusing Steps / DBR)
  └── Lean / WIP-лимиты          ──► Сокращение потерь и ограничение незавершенной работы

[ БИЗНЕС-АНАЛИЗ И АУДИТ ПРОЦЕССОВ ]
  ├── Lean Canvas / VPC / JTBD   ──► Оценка продукта, ценности и пользователей
  ├── SIPOC                      ──► Верхнеуровневый аудит процессов (P ➔ O ➔ C ➔ I ➔ S)
  ├── Диаграмма Исикавы (Fishbone)──► Системный поиск причин сбоев по 6M / 5P
  └── 5 Why                      ──► Глубокий поиск корневых причин (Root Cause Analysis)

[ СТРАТЕГИЯ, ЦЕЛИ И КОМАНДА ]
  ├── OKRs & SMART               ──► Постановка целей (OKR) и точных задач (SMART)
  ├── RACI / RASCI Matrix        ──► Распределение ролей и ответственности (A, R, C, I)
  ├── Матрица Эйзенхауэра        ──► Важно / Срочно (Личный фокус на Q2)
  └── MoSCoW / RICE / Kano       ──► Приоритезация бэклога задач и фич

[ ИСПОЛНЕНИЕ И МЕТОДОЛОГИЯ ]
  ├── Scrum                      ──► Итерации (спринты), роли, события
  └── Kanban / Scrumban          ──► Непрерывный поток, WIP-лимиты, Lead/Cycle Time

[ КОРПОРАТИВНАЯ И СОФТВЕРНАЯ АРХИТЕКТУРА ]
  ├── TOGAF & ArchiMate          ──► Бизнес 🟡 + Софт 🔵 + Инфраструктура 🟢
  ├── BPMN / CMMN / DMN          ──► Процессы, кейсы, правила решений
  ├── Process Flow (Flowchart)   ──► Пошаговые алгоритмы
  └── UML                        ──► Диаграммы Sequence, Class, Use Case

[ ДАННЫЕ И ИНТЕГРАЦИИ ]
  ├── DFD                        ──► Потоки данных
  ├── ERD                        ──► Схемы баз данных (PostgreSQL / Supabase)
  ├── ETL Framework              ──► Конвейеры обработки данных
  └── CRUD                       ──► Операции базы данных и REST API

[ ОРГАНИЗАЦИЯ И ТРЕКИНГ ]
  ├── Jira                       ──► Иерархия (Epics / Tasks / Sub-tasks)
  └── Obsidian                   ──► MOC / ACCESS / PARA
```

### 💡 Как использовать в вашей базе знаний:

В папке `03_Resources / Управление проектами` создай документ `Theory_of_Constraints_TOC.md`.

Используй принцип TOC, когда заметить, что личный бэклог или процессы тормозятся — не пытайтесь делать всё одновременно, найдите единственное бутылочное горлышко и сфокусируйтесь на нем.
