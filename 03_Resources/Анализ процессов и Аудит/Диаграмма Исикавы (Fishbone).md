[[_MOC frameworks]]

### 1. Что это такое?

**Диаграмма Исикавы (Ishikawa Diagram)**, также известная как **Fishbone (Рыбий скелет)** или **Cause-and-Effect Diagram (Диаграмма причин и следствий)** — это графический инструмент анализа, разработанный японским экспертом по качеству Каору Исикавой.

Если **5 Why** работает как вертикальное сверление вглубь («почему ➔ потому что»), то **Диаграмма Исикавы** дает **горизонтальный, системный охват**. Она помогает структурировать десятки потенциальных причин проблемы по категориям, чтобы не упустить ни один возможный фактор.

### 2. Анатомия «Рыбьего скелета»

Диаграмма визуально напоминает скелет рыбы:

- **«Голова»** — чётко сформулированная проблема (следствие/дефект).
    
- **«Позвоночник»** — центральная ось.
    
- **«Большие кости»** — основные категории источников проблем.
    
- **«Малые косточки»** — конкретные причины и подпричины внутри категорий.
    

Plaintext

```
 Категория 1          Категория 2          Категория 3
(Оборудование)       (Процессы/Методы)       (Люди)
     │                    │                    │
     ├── Подпричина       ├── Подпричина       ├── Подпричина
     │                    │                    │
─────┴────────────────────┴────────────────────┴───────────────► [ ПРОБЛЕМА / ДЕФЕКТ ]
     ▲                    ▲                    ▲
     │                    │                    │
     ├── Подпричина       ├── Подпричина       ├── Подпричина
     │                    │                    │
 Категория 4          Категория 5          Категория 6
  (Данные)            (Окружение)         (Материалы/Софт)
```

### 3. Классические категории причин (Фреймворки 6M и 5P)

Чтобы не придумывать категории с нуля, используют готовые стандарты:

#### Для производства и IT-инфраструктуры (Фреймворк 6M):

1. **Manpower (Люди):** Нехватка квалификации, усталость, отсутствие обучения, человеческий фактор.
    
2. **Machine (Оборудование / Железо):** Сбои серверов, проблемы с сетью, аппаратные ограничения, износ.
    
3. **Method (Методы / Процессы):** Неэффективные алгоритмы, отсутствие регламентов, ошибки в BPMN/Flowchart.
    
4. **Material (Материалы / Данные):** Некачественные входящие данные (Inputs в SIPOC), битые CSV, баги сторонних библиотек.
    
5. **Measurement (Измерения):** Неверные метрики, отсутствие логов/мониторинга, некорректные автотесты.
    
6. **Milieu / Mother Nature (Окружение):** Температура в серверной, сбои электропитания, внешние блокировки.
    

#### Для софта и сервисных процессов (Фреймворк 5P):

1. **People (Люди/Команда)**
    
2. **Process (Процессы)**
    
3. **Product / Platform (Платформа/Софт)**
    
4. **Policy (Правила/Регламенты)**
    
5. **Partners / Suppliers (Поставщики API/Интеграции)**

### 5. Связка 5 Why + SIPOC + Исикава

Эффективный аудит процессов проходит в 3 последовательных шага:

1. **SIPOC:** Верхнеуровнево определяем границы процесса и локализуем этап, где произошел сбой.
    
2. **Диаграмма Исикавы:** На брейншторме раскладываем все возможные гипотезы по «костям» (6M), чтобы получить широкую картину.
    
3. **5 Why:** Берём самые вероятные ветки из диаграммы Исикавы и «просверливаем» их вглубь до корневой причины.
    

### 6. Полная матрица фреймворков системного инженера

Твой арсенал бизнес-анализа, продуктового менеджмента и архитектуры:

Plaintext

```
[ БИЗНЕС-АНАЛИЗ И АУДИТ ПРОЦЕССОВ ]
  ├── Lean Canvas / VPC / JTBD   ──► Оценка продукта, ценности и пользователей
  ├── SIPOC                      ──► Верхнеуровневый аудит процессов (P ➔ O ➔ C ➔ I ➔ S)
  ├── Диаграмма Исикавы (Fishbone)──► Широкий системный поиск причин сбоев (6M / 5P)
  └── 5 Why                      ──► Глубокий поиск корневых причин (Root Cause Analysis)

[ СТРАТЕГИЯ, ЦЕЛИ И КОМАНДА ]
  ├── OKRs & SMART               ──► Постановка целей (OKR) и четких задач (SMART)
  ├── RACI / RASCI Matrix        ──► Распределение ролей и ответственности (A, R, C, I)
  ├── Матрица Эйзенхауэра        ──► Важно / Срочно (Личный фокус на Q2)
  └── MoSCoW / RICE / Kano       ──► Приоритезация бэклога задач и фич

[ ИСПОЛНЕНИЕ И МЕТОДОЛОГИЯ ]
  ├── Scrum                      ──► Итерации (спринты), роли, события
  └── Kanban / Scrumban          ──► Непрерывный поток, WIP-лимиты

[ КОРПОРАТИВНАЯ И СОФТВЕРНАЯ АРХИТЕКТУРА ]
  ├── TOGAF & ArchiMate          ──► Бизнес 🟡 + Софт 🔵 + Инфраструктура 🟢
  ├── BPMN / CMMN / DMN          ──► Процессы, кейсы, правила решений
  ├── Process Flow (Flowchart)   ──► Пошаговые алгоритмы
  └── UML                        ──► Диаграммы Sequence, Class, Use Case

[ ДАННЫЕ И ИНТЕГРАЦИИ ]
  ├── DFD                        ──► Потоки данных
  ├── ERD                        ──► Схемы баз данных (PostgreSQL / Supabase)
  ├── ETL Framework              ──► Конвейеры обработки данных
  └── CRUD                       ──► Операции базы данных и REST API

[ ОРГАНИЗАЦИЯ И ТРЕКИНГ ]
  ├── Jira                       ──► Иерархия (Epics / Tasks / Sub-tasks)
  └── Obsidian                   ──► MOC / ACCESS / PARA
```
