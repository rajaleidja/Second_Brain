[[_MOC frameworks]]

### 1. Что это такое?

**CMMN** и **DMN** — это два нотационных стандарта, созданных консорциумом **OMG** (Object Management Group) — теми же авторами, кто разработал классический **BPMN** (Business Process Model and Notation).

Если **BPMN** отвечает за строго последовательные, предсказуемые процессы (_«Сделай шаг A, затем шаг B, если X — иди на шаг C»_), то CMMN и DMN созданы для **нелинейной работы** и **вынесения логики принятия решений**:

- **CMMN (Case Management Model and Notation):** Нотация для управления кейсами / делами в условиях **высокой неопределенности** и гибкого порядка действий (Ad-hoc процессы, где человек сам решает, что делать дальше).
    
- **DMN (Decision Model and Notation):** Нотация для **описания и автоматизации правил принятия решений** (бизнес-правил), отделенная от самого процесса.
    

### 2. DMN (Decision Model and Notation) — Автоматизация правил

**Главная идея:** Вынести все сложные разветвления и условия (_«Если сумма заказа > 1000$ и клиент VIP, то скидка 15%, а если…»_) из кода и нод процесса в прозрачную **Таблицу Решений (Decision Table)**.

#### Зачем нужен DMN?

- **Чистота процессов:** В BPMN или сценарии n8n вместо 20 развилок `If/Else` остаётся **одна нода / вызов DMN**, куда подаются данные на вход и получается готовое решение на выходе.
    
- **Легко менять правила:** Если изменилась процентная ставка или условия выдачи доступа, не нужно переписывать весь процесс — достаточно изменить 1 строчку в DMN-таблице.
    

#### Структура DMN-таблицы (Decision Table):

|**Input (Входные данные)**|**Input (Входные данные)**|**Output (Результат / Решение)**|
|---|---|---|
|**Тариф клиента**|**Сумма покупки**|**Скидка (%)**|
|"VIP"|> 1000 €|20%|
|"VIP"|<= 1000 €|10%|
|"Standard"|> 1000 €|5%|
|"Standard"|<= 1000 €|0%|

> **Пример применения в n8n:**                                                                                     Вместо того чтобы строить гигантское дерево из нод `Switch` и `If`, ты отправляешь JSON с данными пользователя в DMN-движок (например, Camunda DMN Engine) или обрабатываешь его аналогичной табличной логикой и получаешь финальный результат.

### 3. CMMN (Case Management Model and Notation) — Гибкое управление кейсами

**Главная идея:** В отличие от BPMN, где порядок шагов жестко задан стрелками, в CMMN **нет фиксированной последовательности**. Работа строится вокруг **Событий (Events)** и **Стадий (Stages)**, а специалист (Case Worker) сам выбирает, какие задачи из доступных выполнить в данный момент.

#### Где применяется CMMN?

- **Медицинская диагностика:** У врача нет жесткого BPMN-процесса. На основе симптомов и анализов он сам решает, какие обследования направить следующим шагом.
    
- **Расследование страховых случаев / Техподдержка L3:** Решение инцидента зависит от ситуации, нельзя заранее прописать 100% шагов.
    
- **Персональное менторство / Сложный консалтинг:** Действия адаптируются под индивидуальный запрос клиента.
    

#### Ключевые элементы CMMN:

1. **Case File (Файл дела):** Вся информация, собранная по кейсу.
    
2. **Tasks (Задачи):** Действия, которые можно выполнять. Могут быть обязательными, опциональными или активироваться только по условию.
    
3. **Sentries (Часовые / Условия):** Правила вида _«Включить эту задачу, ТОЛЬКО ЕСЛИ получены результаты анализов»_ (On-event / If-condition).
    

### 4. Триада стандартов OMG: BPMN vs CMMN vs DMN

В современной архитектуре автоматизации эти три нотации работают в идеальной связке:

Plaintext

```
┌────────────────────────────────────────────────────────────────────────┐
│                          BPMN / CMMN                                   │
│                  (Управляет ХОДОМ выполнения)                         │
│                                                                        │
│   «Что делать дальше?» ───►  [ Вызов DMN ]                             │
└─────────────────────────────────┬──────────────────────────────────────┘
                                  │
                                  ▼
┌────────────────────────────────────────────────────────────────────────┐
│                             DMN                                        │
│                 (Принимает РЕШЕНИЕ по правилам)                        │
│                                                                        │
│   Принимает: Входные данные  ──►  Возвращает: Готовое решение          │
└────────────────────────────────────────────────────────────────────────┘
```

|**Стандарт**|**Назначение**|**Ключевой вопрос**|**Характер процесса**|
|---|---|---|---|
|**BPMN**|Процессы (Process)|_«КАК и в каком порядке сделать?»_|Строгий, предсказуемый, линейный|
|**CMMN**|Кейсы (Case)|_«ЧТО МОЖНО сделать в этой ситуации?»_|Гибкий, событийно-ориентированный, нелинейный|
|**DMN**|Решения (Decision)|_«КАКОЕ РЕШЕНИЕ принять на основе данных?»_|Декларативный (логические правила)|

### 5. Практический пример связки для курсов и автоматизации в n8n

Представь систему обработки обращений студентов:

1. **BPMN:** Стандартный процесс проверки ДЗ (Студент сдал $\rightarrow$ n8n проверил $\rightarrow$ Оценка отправлена).
    
2. **DMN:** Таблица правил определения категории студента (Если сдал 3 ДЗ подряд за 24 часа + баллы > 90 $\rightarrow$ присвоить статус `"Advanced"`, выдать доступ к VIP-чату).
    
3. **CMMN:** Работа куратора со «сложным студентом» (Студент отстает по программе $\rightarrow$ открывается кейс. Куратор из доступных опций выбирает: _провести созвон_, _дать дополнительный материал_ или _продлить дедлайн_).
    

### 💡 Как использовать в вашей базе знаний:

В папке `03_Resources / Архитектура процессов` создай документ `CMMN_and_DMN.md`.

- **DMN** используй как концептуальную основу для проектирования таблиц конфигураций в n8n (чтобы не загромождать workflows).
    
- **CMMN** используй для описания процессов с высокой долей ручной работы и адаптивных сценариев.
