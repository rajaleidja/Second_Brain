[[_MOC frameworks]]

### 1. Что это такое?

**DFD (Data Flow Diagram / Диаграмма потоков данных)** — это графическая нотация, которая показывает, **как данные передвигаются внутри системы**: откуда они поступают, где обрабатываются, в каких хранилищах остаются и куда передаются на выходе.

В отличие от BPMN или UML Sequence Diagram, DFD **не показывает временную последовательность, циклы или условие `If/Else`**. DFD отвечает на один главный вопрос: **«Что происходит с данными в процессе их трансформации?»**

### 2. Зачем нужен DFD?

1. **Проектирование архитектуры:** Понять состав модулей системы, входов/выходов и баз данных до написания кода или сборки workflows в n8n.
    
2. **Анализ безопасности:** Показать границы системы (Trust Boundaries) и увидеть, через какие узлы проходят чувствительные данные (пароли, токены, персональные данные).
    
3. **Мостик между бизнесом и разработкой:** Бизнесу понятно, _какая информация_ передается, а технической команде — _какие API и структуры БД_ нужно реализовать.
    

### 3. Элементы DFD (Нотация Йордона / Гейна-Сарсона)

DFD состоит всего из **4 базовых символов**:

Plaintext

```
┌───────────────────┐        Поток данных (Data Flow)        ┌────────────────┐
│  Внешняя сущность │ ─────────────────────────────────────► │    Процесс     │
│ (External Entity) │                                        │   (Process)    │
└───────────────────┘                                        └─────┬──────────┘
                                                                  │
                                                                  │Поток данных
                                                                  ▼
                                                          ┌─────────────────┐
                                                          │ Хранилище данных│
                                                          │  (Data Store)   │
                                                          └─────────────────┘
```

1. **Внешняя сущность (External Entity):** Источник или получатель данных вне рамок проектируемой системы (например: _Пользователь_, _Telegram API_, _Платежный шлюз Stripe_).
    
2. **Процесс (Process):** Операция, которая трансформирует входные данные во выходные (например: _«Валидация JSON»_, _«Генерация ответа через Gemini API»_, _«Расчет итоговой скидки»_).
    
3. **Хранилище данных (Data Store):** Место постоянного или временного хранения информации (например: _Таблица `users` в PostgreSQL_, _Redis-кэш_, _Google Sheet_).
    
4. **Поток данных (Data Flow):** Стрелка, показывающая направление передачи и тип данных (например: _`Пользовательский запрос [text]`_, _`API-ключ`_, _`ID транзакции`_).
    

### 4. Уровни детализации DFD

DFD строится по принципу **иерархической детализации (декомпозиции)**:

- **Контекстная диаграмма (Уровень 0 / Context Diagram):** Самый верхний уровень. Вся система представлена в виде **одного круга/блока**, вокруг которого расположены внешние сущности.
    
- **DFD Уровень 1:** Главный процесс распадается на 3–7 основных подпроцессов, раскрываются ключевые хранилища данных.
    
- **DFD Уровень 2:** Детализация отдельных сложных подпроцессов до уровня конкретных алгоритмических трансформаций.
    

### 5. Практический пример: DFD Уровень 1 для ИИ-агента парсинга отзывов в n8n

Представь автоматизированный сервис, который принимает CSV-файл с отзывами, анализирует их с помощью Gemini API и сохраняет результаты в PostgreSQL.

Plaintext

```
                               ┌─────────────────┐
                               │  Администратор  │
                               └────────┬────────┘
                                        │
                                        │ 1. Загрузка CSV-файла
                                        ▼
                                ┌───────────────┐
                                │ 1.0 Валидатор │
                                │   и Парсер    │
                                └───────┬───────┘
                                        │
                                        │ 2. Сырой текст отзыва
                                        ▼
┌───────────────┐               ┌───────────────┐            ┌──────────────────┐
│  Gemini API   │ ◄───────────► │ 2.0 ИИ-Анализ │ ─────────► │  D1: PostgreSQL  │
│  (LLM Model)  │  Промпт /     │  тональности  │  Структур- │  (Таблица        │
└───────────────┘  JSON-ответ   └───────────────┘  ный JSON  │   `feedbacks`)   │
                                                           └──────────────────┘
```

#### Разбор потоков:

- **Процесс 1.0:** Принимает CSV, проверяет структуру и разбивает его на отдельные записи.
    
- **Процесс 2.0:** Формирует промпт, отправляет его во внешнюю систему **Gemini API**, получает JSON с тегами и эмоциональной оценкой.
    
- **Хранилище D1:** Записывает финальный результат в базу данных.
    

### 6. Правила и частые ошибки при построении DFD

- ❌ **Запрещено прямое соединение двух Хранилищ:** Данные не могут перетекать из одной БД в другую сами по себе, между ними всегда должен быть Процесс.
    
- ❌ **Запрещено прямое соединение Внешних сущностей с Хранилищем:** Пользователь не может напрямую читать из БД — всегда нужен Процесс (API / Эндпоинт).
    
- ✅ **Сохранение баланса (Balancing):** Все входные и выходные потоки процесса на Уровне 0 должны присутствовать на Уровне 1.
    

### 💡 Как использовать в вашей базе знаний:

В папке `03_Resources / Архитектура процессов` создай документ `DFD_Data_Flow_Diagram.md`.

DFD идеально подходит для совместного использования с **CRUD** и **BPMN**:

1. **BPMN** показывает _последовательность шагов_.
    
2. **DFD** показывает _структуру и трансформация данных на этих шагах_.
    
3. **CRUD** определяет _конкретные операции над БД в рамках DFD-процессов_.
