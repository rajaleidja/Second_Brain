[[_MOC frameworks]]

### 1. Что это такое?

**ERD (Entity-Relationship Diagram / Диаграмма «Сущность — Связь»)** — это визуальная модель данных, которая описывает **структуру базы данных**: ключевые объекты системы (сущности), их свойства (атрибуты) и то, как они связаны друг с другом (связи).

Если **DFD** показывает, _как данные передвигаются_, а **CRUD** — _какие базовые операции над ними выполняются_, то **ERD** определяет **фундаментальный каркас (схему)**, в котором эти данные хранятся в SQL/NoSQL базах (PostgreSQL, Supabase, MySQL).

### 2. Зачем нужен ERD?

1. **Проектирование архитектуры «до кода»:** Исключает ошибки в структуре таблиц еще на этапе идеи, спасая от мучительных рефакторингов и миграций в будущем.
    
2. **Устранение дублирования (Нормализация):** Позволяет правильно распределить данные по таблицам, избегая аномалий обновления и избыточности.
    
3. **Единый стандарт коммуникации:** Понятная схема для разработчиков, архитекторов и аналитиков (легко переводится в реальный SQL-скрипт `CREATE TABLE`).
    

### 3. Три ключевых элемента ERD

Plaintext

```
┌─────────────────────────┐               ┌─────────────────────────┐
│     СУЩНОСТЬ (Entity)   │               │     СУЩНОСТЬ (Entity)   │
│         Пользователь    │               │          Заказ          │
├─────────────────────────┤  СВЯЗЬ (1:N)  ├─────────────────────────┤
│ PK  user_id (INT)       │ ────────────< │ PK  order_id (INT)      │
│     email (VARCHAR)     │               │ FK  user_id (INT)       │
│     created_at (TIMESTAMP)              │     total_amount (DEC)  │
└─────────────────────────┘               └─────────────────────────┘
```

1. **Сущность (Entity / Таблица):** Объект реального мира или системы, о котором мы храним информацию (например, _User_, _Course_, _Feedback_, _Lesson_).
    
2. **Атрибут (Attribute / Колонка):** Свойство сущности (например, `email`, `created_at`, `status`).
    
    - **PK (Primary Key / Первичный ключ):** Уникальный идентификатор записи (`id`, `uuid`).
        
    - **FK (Foreign Key / Внешний ключ):** Ссылка на первичный ключ другой таблицы для создания связи.
        
3. **Связь (Relationship / Кардинальность):** Логическое отношение между сущностями.
    

### 4. Типы связей (Кардинальность / Crow's Foot Notation)

Для обозначения связей чаще всего используют нотацию **«Куриная лапка» (Crow's Foot)**:

- **1:1 (Один к одному):** Встречается редко. Запись в Таблице А соответствует строго одной записи в Таблице Б (например, _Пользователь $\rightarrow$ Профиль настройки_).
    
- **1:N (Один ко многим):** Самый частый тип связи. Одна запись в Таблице А может быть связана с несколькими записями в Таблице Б (например, _Один Пользователь $\rightarrow$ Много Заказов_).
    
- **M:N (Многие ко многим):** Одна запись в А связана со множеством в Б, и наоборот (например, _Студенты $\rightarrow$ Курсы_).
    
    > ⚠️ **Правило реляционных БД:** Связь M:N нельзя реализовать напрямую. Ее всегда разбивают на две связи 1:N через промежуточную **связующую таблицу (Junction Table)** — например, `course_enrollments`.
    

### 5. Практический пример: ERD для сервиса курсов и анализа отзывов в PostgreSQL

Схема базы данных для системы обучения с ИИ-анализом отзывов:

Plaintext

```
┌────────────────────────┐         ┌────────────────────────┐
│        users           │         │  course_enrollments    │
├────────────────────────┤         ├────────────────────────┤
│ PK  id (UUID)          │1       N│ PK  id (UUID)          │
│     email (VARCHAR)    ├─────────┤ FK  user_id (UUID)     │
│     name (VARCHAR)     │         │ FK  course_id (UUID)   │
│     created_at (TIME)  │         │     enrolled_at (TIME) │
└────────────────────────┘         └───────────▲────────────┘
                                               │N
                                               │
                                               │1
┌────────────────────────┐         ┌───────────┴────────────┐
│       feedbacks        │         │        courses         │
├────────────────────────┤         ├────────────────────────┤
│ PK  id (UUID)          │N       1│ PK  id (UUID)          │
│ FK  course_id (UUID)   ├─────────┤     title (VARCHAR)    │
│     raw_text (TEXT)    │         │     price (NUMERIC)    │
│     sentiment (VARCHAR)│         │     created_at (TIME)  │
│     created_at (TIME)  │         └────────────────────────┘
└────────────────────────┘
```

#### Разбор структуры:

- **users $\leftrightarrow$ courses:** Связь **M:N** реализована через связующую таблицу `course_enrollments` (один студент может быть на разных курсах, на одном курсе много студентов).
    
- **courses $\leftrightarrow$ feedbacks:** Связь **1:N** (у одного курса может быть много отзывов, но конкретный отзыв относится только к одному курсу).
    
- **Атрибут `feedbacks.sentiment`:** Сюда ИИ-агент n8n записывает результат анализа (например, `positive`, `negative`, `neutral`).
    

### 6. Иерархия инструментов моделирования (Полная картина)

Теперь вся цепочка системного анализа и проектирования зафиксирована:

1. **Lean Canvas / Empathy Map / JTBD / VPC:** Выявляют боли пользователя и формируют бизнес-модель.
    
2. **SIPOC / 5 Why:** Аудируют и оптимизируют верхнеуровневый процесс.
    
3. **BPMN / CMMN / DMN:** Задают алгоритм, развилки, правила решений и гибкие сценарии.
    
4. **DFD:** Показывает потоки и трансформацию данных между модулями.
    
5. **ERD (текущий):** Фиксирует физическую структуру таблиц и связей в базе данных.
    
6. **CRUD:** Задает стандарты API-эндпоинтов для манипуляции этой базой.
    
7. **User Stories / Use Cases / Jira:** Нарезают всё это в конкретные задачи для бэклога разработки.
