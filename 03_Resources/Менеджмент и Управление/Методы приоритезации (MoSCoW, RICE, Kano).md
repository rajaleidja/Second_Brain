[[_MOC frameworks]]

### 1. Что это такое?

Если **Матрица Эйзенхауэра** отвечает за личный тайм-менеджмент (_«Что мне делать сегодня?»_), то **методы приоритезации (MoSCoW, RICE, Kano)** — это продуктовые и инженерные фреймворки. Они отвечают на вопрос: **«Какие фичи, задачи или Epics делать в первую очередь, а какие выбросить из бэклога?»**

Использование этих методов исключает субъективность («мне кажется, это важно») и переводит планирование бэклога в Jira на язык цифр, рисков и клиентской ценности.

### 2. MoSCoW: Быстрая сортировка бэклога (Для релизов и MVP)

Метод делит весь список требований или задач в спринте/релизе на 4 четкие категории:

Plaintext

```
  ┌─────────────────────────────────────────────────────────────┐
  │ M - MUST HAVE (Обязательно)                                  │
  │ Без этого релиз не имеет смысла / продукт не работает.       │
  ├─────────────────────────────────────────────────────────────┤
  │ S - SHOULD HAVE (Желательно)                                │
  │ Важные фичи, но у продукта есть жизнеспособный обходной путь.│
  ├─────────────────────────────────────────────────────────────┤
  │ C - COULD HAVE (Можно сделать)                              │
  │ Мелкие улучшайзеры ("Nice to have"), если останется время.  │
  ├─────────────────────────────────────────────────────────────┤
  │ W - WON'T HAVE (Не в этот раз)                              │
  │ Отклоненные фичи для текущего релиза/спринта.               │
  └─────────────────────────────────────────────────────────────┘
```

- **Пример для бота/workflow в n8n:**
    
    - **Must:** Прием Webhook + запись в БД PostgreSQL (**ERD**).
        
    - **Should:** Обогащение ответа через Gemini API.
        
    - **Could:** Отправка красиво оформленного алерта в Telegram.
        
    - **Won't:** Построение динамического графического дашборда на React.
        

### 3. RICE Scoring: Математический расчет приоритета

Фреймворк оценщиков из Intercom. Каждой задаче присваивается балл по формуле:

$$\text{RICE Score} = \frac{\text{Reach} \times \text{Impact} \times \text{Confidence}}{\text{Effort}}$$

Plaintext

```
┌────────────────────────┬──────────────────────────────────────────┐
│ R - Reach (Охват)      │Скольких пользователей/процессов затронет?│
│ I - Impact (Влияние)   │ Насколько сильно поможем? (0.25 до 3)    │
│ C - Confidence(Уверен.)│ Насколько мы уверены в оценках? (50-100%)│
├────────────────────────┼──────────────────────────────────────────┤
│ E - Effort (Усилия)    │  Человеко-дни / Story Points на задачу   │
└────────────────────────┴──────────────────────────────────────────┘
```

#### Шкала оценок:

- **Impact:** `3` = огромный эффект, `2` = высокий, `1` = средний, `0.5` = низкий.
    
- **Confidence:** `100%` = есть четкая спецификация/данные, `80%` = средняя уверенность, `50%` = "палец в небо".
    

#### Пример расчета RICE для двух задач в бэклоге:

1. **Задача А:** Оптимизировать запрос в DB (**ERD**):
    
    - $\text{Reach} = 1000$ запросов/день
        
    - $\text{Impact} = 2$ (высокий эффект)
        
    - $\text{Confidence} = 100\%$ ($1.0$)
        
    - $\text{Effort} = 1$ день
        
    - **RICE Score** $= \frac{1000 \times 2 \times 1.0}{1} = \mathbf{2000}$
        
2. **Задача Б:** Переписать интерфейс на красивую тему:
    
    - $\text{Reach} = 200$ пользователей
        
    - $\text{Impact} = 0.5$ (низкий)
        
    - $\text{Confidence} = 80\%$ ($0.8$)
        
    - $\text{Effort} = 4$ дня
        
    - **RICE Score** $= \frac{200 \times 0.5 \times 0.8}{4} = \mathbf{20}$
        

> 💡 **Вывод:** Задача А выигрывает со счетом 2000 против 20. Она берется в разработку первой.

### 4. Модель Кано (Kano Model): Приоритезация по эмоциям пользователей

Модель Янито Кано помогает понять, как наличие или отсутствие фичи влияет на удовлетворенность клиентов:

Plaintext

```
Удовлетворенность
       ▲
       │        / 🚀 Восторгающие (Delighters)
       │       /
       │      /   ⚡ Линейные (Performance)
       │     /  /
       │    / /
       │   //
───────┼──//────────────────────────► Функциональность
       │ // 🛑 Обязательные (Must-be)
       │//
       ▼
```

1. **Обязательные (Must-be / Basic):** Пользователь принимают их как должное (например, работающий вход по логину или валидация формата email). Если их нет — катастрофа, если есть — никто не хвалит.
    
2. **Линейные (Performance):** Чем лучше сделано, тем больше счастья (скорость работы сайта, время ответа API, емкость аккумулятора).
    
3. **Восторгающие (Delighters / Attractive):** Неожиданные фичи, вызывающие «Вау-эффект» (например, ИИ сам сгенерировал резюме ответа или нашел скрытую аномалию). Их отсутствие не расстраивает, но наличие побеждает конкурентов.
    

### 5. Сводная система фреймворков принятия решений

Теперь твой арсенал менеджмента, аналитики и разработки полностью укомплектован:

Plaintext

```
[ ПРИОРИТЕТИЗАЦИЯ И ТАЙМ-МЕНЕДЖМЕНТ ]
  ├── Матрица Эйзенхауэра        ──► Важно / Срочно (Фокус на Q2)
  ├── MoSCoW                     ──► Быстрый состав релиза (Must/Should/Could/Won't)
  ├── RICE Scoring               ──► Численный приоритет задач бэклога в Jira
  └── Kano Model                 ──► Оценка фич по эмоциональному отклику пользователей

[ БИЗНЕС-СТРАТЕГИЯ И АУДИТ ]
  ├── Lean Canvas / VPC / JTBD   ──► Продукт, ценность и целевая аудитория
  └── SIPOC / 5 Why              ──► Верхнеуровневый аудит процессов

[ АРХИТЕКТУРА И МОДЕЛИРОВАНИЕ ]
  ├── TOGAF & ArchiMate          ──► Макро-уровень (Бизнес + Софт + Инфраструктура)
  ├── BPMN / CMMN / DMN          ──► Исполняемые процессы, кейсы, правила
  ├── Process Flow (Flowchart)   ──► Алгоритмы и блок-схемы
  └── UML                        ──► Диаграммы классов, Use Cases и Sequence

[ ДАННЫЕ И ИНТЕГРАЦИИ ]
  ├── DFD                        ──► Потоки данных
  ├── ERD                        ──► Проектирование БД (SQL/Supabase)
  ├── ETL Framework              ──► Конвейеры обработки (Extract-Transform-Load)
  └── CRUD                       ──► Операции базы данных и REST API

[ УПРАВЛЕНИЕ И БАЗА ЗНАНИЙ ]
  ├── Jira                       ──► Иерархия задач (Epics / Tasks / Sub-tasks)
  └── Obsidian                   ──► MOC / ACCESS / PARA
```

### 💡 Как использовать в вашей базе знаний:

В папке `03_Resources / Управление проектами` создай документ `Prioritization_Methods_MoSCoW_RICE_Kano.md`.

- Добавляй полей `RICE Score` или метки `MoSCoW` (`must-have`, `should-have`) к задачам в бэклоге Jira, чтобы планировать очередность работы.
