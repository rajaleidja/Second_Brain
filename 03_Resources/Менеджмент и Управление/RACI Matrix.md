[[_MOC frameworks]]

### 1. Что это такое?

**Матрица RACI (RACI Matrix / Responsibility Assignment Matrix)** — это фреймворк распределения ролей и ответственности в проектах и бизнес-процессах. Она определяет, кто за что отвечает при выполнении задачи, согласовании решений или реализации этапа.

Использование RACI исключает ситуацию «размытой ответственности» (когда задача зависла, потому что «все думали, что делает кто-то другой») и убирает лишние согласования.

### 2. Расшифровка аббревиатуры RACI

Каждая буква обозначает одну из 4 возможных ролей человека или команды относительно задачи:

Plaintext

```
┌─────────────────────────────────────────────────────────────────┐
│ R - Responsible (Исполнитель)                                   │
│ Тот, кто непосредственно делает работу и отвечает за результат. │
│ ⚠️ На задачу может быть 1 или несколько R.                       │
├─────────────────────────────────────────────────────────────────┤
│ A - Accountable (Ответственный / Утверждающий)                  │
│ Тот, кто несет РЕШАЮЩУЮ ответственность за итоговый результат. │
│ Имеет право вето и принимает работу.                            │
│ 🛑 СТРОГОЕ ПРАВИЛО: На одну задачу может быть ТОЛЬКО ОДИН 'A'!  │
├─────────────────────────────────────────────────────────────────┤
│ C - Consulted (Консультант)                                     │
│ Эксперт, с которым ОБЯЗАТЕЛЬНО консультируются ДО начала        │
│ работы или во время её выполнения (двусторонний обмен).         │
├─────────────────────────────────────────────────────────────────┤
│ I - Informed (Информируемый)                                    │
│ Тот, кого просто СТАВЯТ В ИЗВЕСТНОСТЬ о ходе или статусе        │
│ после выполнения (одностороннее уведомление).                   │
└─────────────────────────────────────────────────────────────────┘
```

### 3. Пример матрицы RACI для IT-проекта / Автоматизации

Пример распределения ролей при проектировании и запуске нового сервиса или n8n-автоматизации:

|**Задача / Этап**|**Системный аналитик / Архитектор**|**Lead Backend Dev**|**QA / Тестировщик**|**Product Owner**|**DevOps / Сисадмин**|
|---|---|---|---|---|---|
|**Сбор требований и BPMN**|**A / R**|C|I|C|I|
|**Проектирование ERD-схемы БД**|**R**|**A**|I|I|C|
|**Разработка n8n workflow / API**|C|**A / R**|I|I|I|
|**Тестирование и валидация**|C|C|**A / R**|I|I|
|**Деплой на прод и настройка CI/CD**|I|C|I|I|**A / R**|
|**Приемка релиза (Sign-off)**|C|C|C|**A**|I|

> 💡 **Примечание:** Одному человеку могут одновременно назначаться роли **A** и **R** (Accountable & Responsible), если он сам разрабатывает задачу и сам отвечает за её окончательный результат (как часто бывает в неболших проектах).

### 4. Расширенные модификации: RASCI и DACI

1. **RASCI:** Добавляется роль **Support (S)** — человек или команда, предоставляющая вспомогательные ресурсы или инфраструктуру для Исполнителя (**R**).
    
2. **DACI:** Вариант для принятия быстрых решений:
    
    - **D (Driver):** Организатор процесса принятия решения.
        
    - **A (Approver):** Тот, кто принимает окончательное решение (аналог **A** в RACI).
        
    - **C (Contributors):** Эксперты и консультанты.
        
    - **I (Informed):** Информируемые участники.
        

### 5. Полный стек управленческих и архитектурных фреймворков

Твой арсенал фреймворков от целеполагания до реализации софта и процессов:

Plaintext

```
[ УПРАВЛЕНИЕ, ЦЕЛИ И КОМАНДА ]
  ├── OKRs & SMART               ──► Амбициозные цели (OKR) и точные задачи (SMART)
  ├── RACI / RASCI Matrix        ──► Распределение ролей и ответственности (A, R, C, I)
  ├── Матрица Эйзенхауэра        ──► Важно / Срочно (Личный фокус на Q2)
  └── MoSCoW / RICE / Kano       ──► Приоритезация бэклога задач и фич

[ БИЗНЕС-АНАЛИЗ И АУДИТ ]
  ├── Lean Canvas / VPC / JTBD   ──► Продукт, ценность, клиенты
  └── SIPOC / 5 Why              ──► Аудит процессов и поиск корневых причин

[ АРХИТЕКТУРА И МОДЕЛИРОВАНИЕ ]
  ├── TOGAF & ArchiMate          ──► Бизнес 🟡 + Софт 🔵 + Инфраструктура 🟢
  ├── BPMN / CMMN / DMN          ──► Исполняемые процессы, кейсы, правила решений
  ├── Process Flow (Flowchart)   ──► Пошаговые алгоритмы
  └── UML                        ──► Диаграммы Sequence, Class, Use Case

[ ДАННЫЕ И ИНТЕГРАЦИИ ]
  ├── DFD                        ──► Потоки данных
  ├── ERD                        ──► Схемы баз данных (PostgreSQL / Supabase)
  ├── ETL Framework              ──► Конвейеры обработки данных
  └── CRUD                       ──► Операции базы данных и REST API

[ ОРГАНИЗАЦИЯ И ТРЕКИНГ ]
  ├── Jira                       ──► Иерархия (Epics / Tasks / Sub-tasks)
  └── Obsidian                   ──► MOC / ACCESS / PARA
```

### 💡 Как использовать в вашей базе знаний:

В папке `03_Resources / Управление проектами` создай документ `RACI_Matrix.md`.

Используй RACI в описании сложных Epics в Jira или регламентах процессов, чтобы у каждого этапа был ровно один утверждающий (**A**) и четкие исполнители (**R**).
